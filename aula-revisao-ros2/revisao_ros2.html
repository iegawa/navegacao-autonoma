Revisão de conceitosComunicação

Como o ROS 2 funciona

O ROS 2 é um conjunto de programas (nós) que trocam mensagens pela rede. Cada nó faz uma tarefa, e a comunicação acontece pelo middleware DDS.

nó: lidar_driverpublica /scan
↓ mensagem (tópico)
nó: mapeadorassina /scan
↓ mensagem (tópico)
nó: controleassina /map

Os nós não se conhecem diretamente. Eles só combinam nomes de tópicos e tipos de mensagem.

Peças básicas

  • Nó: um processo que faz uma coisa (ler sensor, planejar, controlar).
  • Mensagem: dados com tipo fixo, como sensor_msgs/LaserScan.
  • Domínio: ROS_DOMAIN_ID separa redes. Nós de domínios diferentes não se veem.
  • Descoberta: é automática. O DDS encontra quem publica e quem assina.

ros2 topic list
ros2 node info /mapeador
Revisão de conceitosTópicos, serviços e ações

Três formas de comunicação

MecanismoPadrãoQuando usarExemplo no nosso stack
TópicoPublicar e assinar, contínuo, sem respostaDados que chegam o tempo todo/scan, /odom, /cmd_vel
ServiçoPedido e resposta, uma vezAções curtas e rápidas/dobot/clear_alarms, /dobot/emergency_stop
AçãoGoal, feedback durante a execução e result, com cancelamentoTarefas longas que demoram e podem ser canceladas/navigate_to_pose

Tópico

Quem publica não espera confirmação. Vários assinantes podem ouvir o mesmo tópico.

Serviço

O cliente envia um request e espera o response. Só um servidor atende.

Ação

O cliente envia o goal, recebe feedback enquanto o robô anda e recebe o result no fim.

SimulaçãoSDF e plugins

Um mundo SDF com robô, sensor e plugin

O arquivo SDF contém a física e a geometria do robô. Um robô é composto principalmente por links (partes rígidas, como chassi e rodas) e joints (articulações que conectam os links).

Cada <link> geralmente tem três tags principais:

<visual>

Como o robô aparece na tela: malhas 3D, cores e formas.

<collision>

A caixa delimitadora usada pelo motor de física para calcular batidas e interações.

<inertial>

A massa e a matriz de inércia, para simular o peso e a dinâmica.

<!-- trecho simplificado -->
<sdf version="1.9">
  <world name="sala">
    <plugin filename="gz-sim-sensors-system" name="gz::sim::systems::Sensors">
      <render_engine>ogre2</render_engine>
    </plugin>
    <model name="robo">
      <link name="base_link">
        <sensor name="lidar" type="gpu_lidar">
          <topic>scan</topic>
          <update_rate>10</update_rate>
        </sensor>
      </link>
      <plugin filename="gz-sim-diff-drive-system" name="gz::sim::systems::DiffDrive">
        <left_joint>left_wheel_joint</left_joint>
        <right_joint>right_wheel_joint</right_joint>
      </plugin>
    </model>
  </world>
</sdf>
SimulaçãoCriar um modelo

Como um modelo entra no Gazebo

  1. Malha visual (mesh): o formato do robô, feito no CAD ou Blender e exportado como .dae, .obj ou .stl. Use metros como unidade.
  2. Colisão: formas simples (box, cylinder, sphere). Malhas complexas deixam a física lenta.
  3. Inércia: massa e momento de inércia. Sem isso, o robô tomba ou tremelica.
  4. SDF: o arquivo model.sdf junta tudo em links e joints, com sensores e plugins.
Estrutura de pastas 
caixa_robo/
├── model.config      # nome, versão e qual .sdf usar
├── model.sdf         # links, sensores, plugins
└── meshes/
    └── base.dae      # aparência do robô
<!-- model.sdf (trecho) -->
<model name="caixa_robo">
  <link name="base_link">
    <inertial>
      <mass>5.0</mass>
      <inertia>
        <ixx>0.05</ixx><iyy>0.05</iyy><izz>0.08</izz>
      </inertia>
    </inertial>

    <visual name="visual">
      <geometry>
        <mesh><uri>model://caixa_robo/meshes/base.dae</uri></mesh>
      </geometry>
    </visual>

    <collision name="collision">
      <geometry>
        <box><size>0.30 0.20 0.10</size></box>
      </geometry>
    </collision>
  </link>
</model>
Para o Gazebo achar a pasta do modelo, aponte o caminho com GZ_SIM_RESOURCE_PATH e teste com gz sim mundo.sdf.

Raciocínio espacialTF2

A hierarquia de frames da robótica móvel

Cada frame é um referencial. Cada seta é uma transformação entre dois deles, e alguém precisa publicá-la.

map
→
map → odomPublicada pelo localizador (AMCL ou SLAM). Corrige o erro acumulado. Pode dar saltos.
odom
→
odom → base_linkPublicada pela odometria (rodas e encoders). Contínua, mas com drift.
base_link
→
base_link → laser_linkEstática. Vem da descrição do robô (URDF) via robot_state_publisher.
laser_link

map

Referencial global e fixo do mapa salvo.

odom

Começa quando o robô liga. Anda sem saltos, mas acumula erro.

base_link

Centro do robô. O controle move essa base.

laser_link

Onde o LiDAR está montado no robô.

ros2 run tf2_tools view_frames   # gera a árvore completa
ros2 run tf2_ros tf2_echo map base_link   # transformação ao vivo
Raciocínio espacialQuaternions

Orientação no plano: do ângulo ao quaternion

Arraste o slider yaw ou clique em um ângulo pronto. O robô gira na vista de cima e os valores do quaternion mudam.

Vista de cima. A seta laranja é a frente do robô (eixo x).


          
Em ROS 2 a ordem é x, y, z, w. Para girar só em torno de z: qz = sin(θ/2) e qw = cos(θ/2). A norma tem que ser 1. Por isso o quaternion evita problemas de gimbal lock.

# nav_stack.launch.py (simplificado)
from launch import LaunchDescription
from launch_ros.actions import LifecycleNode, Node

def generate_launch_description():
    amcl = LifecycleNode(package='nav2_amcl', executable='amcl',
                         name='amcl', namespace='')
    planner = LifecycleNode(package='nav2_planner', executable='planner_server',
                            name='planner_server', namespace='')
    controller = LifecycleNode(package='nav2_controller', executable='controller_server',
                               name='controller_server', namespace='')
    manager = Node(package='nav2_lifecycle_manager',
                   executable='lifecycle_manager',
                   name='lifecycle_manager_navigation',
                   parameters=[{'autostart': True,
                                'node_names': ['amcl', 'planner_server',
                                               'controller_server']}])
    return LaunchDescription([amcl, planner, controller, manager])

        

          
Simular o lifecycle manager

          
Clique em Executar launch. Com autostart: True, o manager leva cada servidor da lista até Active.

ActionNavigateToPose

      
Enviar um goal e acompanhar a execução

      

      

        
Goal
PoseStamped: posição e orientação do destino, no frame map.

        
Feedback
Chega durante a execução: distance_remaining, number_of_recoveries.

        
Result
Chega no fim: error_code (sucesso, falha ou cancelado).

      

      

        

          
Preencha o destino e clique em Enviar goal. A barra mostra o progresso. Cancelar interrompe a ação. O robô parte de (0, 0).

          

            
            
            
          

          

          

            
            
          

          

          
Status: aguardando goal.

        

        
# cliente em rclpy (simplificado)
from nav2_msgs.action import NavigateToPose
from rclpy.action import ActionClient

client = ActionClient(node, NavigateToPose, 'navigate_to_pose')
goal = NavigateToPose.Goal()
goal.pose.header.frame_id = 'map'
goal.pose.pose.position.x = 3.0
goal.pose.pose.position.y = 2.0
goal.pose.pose.orientation.z = 0.707  # yaw de 90°
goal.pose.pose.orientation.w = 0.707

future = client.send_goal_async(goal, feedback_callback=on_feedback)
# depois: future.result().get_result_async() → error_code

      

    

  


  
  

    

      
ConexãoTurtleBot3

      
Conectar no TurtleBot

      

      
    
        
  1. Instalar os pacotes (uma vez no seu computador).
    2. 
        
  2. Definir as variáveis no terminal. ROS_DOMAIN_ID é 10 × número do grupo. Ex.: grupo 2 → 20.
    3. 
        
  3. Confirmar que o robô aparece na rede do grupo.
    4. 
        
  4. Dirigir pelo teclado com o teleop.
    5. 
      

      
# 1. instalar
sudo apt install ros-jazzy-rmw-cyclonedds-cpp ros-jazzy-turtlebot3-teleop

# 2. variáveis (use o seu grupo)
export ROS_DOMAIN_ID=20                       # 10 × número do grupo
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export TURTLEBOT3_MODEL=burger

# 3. conferir os tópicos
ros2 topic list                               # deve listar /scan, /odom, /cmd_vel...
ros2 topic echo /scan --once

# 4. dirigir pelo teclado
ros2 run turtlebot3_teleop teleop_keyboard

      
Se ros2 topic list não mostrar os tópicos, confira se o ROS_DOMAIN_ID é o mesmo do robô e se o RMW_IMPLEMENTATION está igual nos dois lados.

Passo 3 · Terminal 2: comandos

          
cd /home/inteli/Antigravity/Dobot_Magician
source /opt/ros/jazzy/setup.bash
source install/setup.bash

# 1. Movimento articular (giro seguro na base J1):
ros2 service call /dobot/move_to_joints magician_lite_msgs/srv/SetJoints "{j1: -0.30, j2: -0.10, j3: 0.75, j4: 0.0}"

# 2. Movimento cartesiano (subir 1 cm no eixo Z, modo MOVJ):
ros2 service call /dobot/move_to_pose magician_lite_msgs/srv/SetPose "{x: 0.172, y: -0.073, z: 0.060, r: -0.40, mode: 1}"

# 3. Parada de emergência:
ros2 service call /dobot/emergency_stop std_srvs/srv/Trigger "{}"

# 4. Limpar alarmes (se o LED ficar vermelho):
ros2 service call /dobot/clear_alarms std_srvs/srv/Trigger "{}"

Espaço
map → odom → base_link → laser_link. Quaternions guardam a orientação.

        
Nav2
Servidores em lifecycle, um launch para subir tudo, e a action NavigateToPose.
